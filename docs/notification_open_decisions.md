# 알림 발송 전 결정 필요 항목 (2026-09-02 · 2026-09-05 잠정 결정 전환)

설계는 `docs/notification_design.md`, 구현은 드라이런까지 끝났다(`agents/notifier.py`).
**실제 발송을 켜기 전에 정해야 하는 것들**을 여기 모은다.

## 읽는 법 — 답을 안 해도 된다

13개 질문에 각각 답을 받는 방식은 부담이 커서 진도가 안 나갔다. **묵시적 동의로
바꾼다.**

> **9/8(화) 24시까지 이의가 없으면 아래 잠정 결정을 그대로 확정한다.**
> 읽고 넘기면 동의로 본다. 반대는 **항목 번호 + 고를 안** 한 줄이면 된다.
> 확정 후에도 바꿀 수 있다 — 다만 그때는 경계일을 기록하고 바꾼다(비소급 방침).

각 항목에 **(잠정 결정)** 으로 표시했다. 근거는 항목마다 적어두었으니 반대할 때
읽을 것만 읽으면 된다.

## 이 방식이 적용되지 않는 세 가지

| | 항목 | 왜 |
|---|---|---|
| **답이 있어야 진행** | A-1 도메인 · D-4 요금제 | 남이 가진 정보가 있어야 정해진다. 각각 한 줄 질문이다 |
| **외부 확인 필요** | C-3 교수님 확인 | 팀 합의로 대체할 수 없다 |
| **묵시적 동의 금지** | **실제 발송 스위치** | 메일은 나가면 회수가 안 된다 |

**마지막 줄이 이 문서에서 제일 중요하다.** 설계·구현·드라이런·로그까지는 잠정
결정으로 굴리되, **첫 실제 발송만은 최소 한 명의 명시적 동의를 받고 켠다.**
여기서 사고가 나면 되돌릴 방법이 없다.

## A. 인프라 착수를 막는 것 (설계 문서 §8-7)

### A-1. 발송 도메인

메일이 스팸함으로 가지 않으려면 SPF/DKIM 정렬이 되어야 하고, 그러려면 발신 도메인을
우리가 통제해야 한다. 사이트 도메인(`aicp-econpilot.github.io`)으로는 메일을 못 보낸다.

| | 선택지 | 장점 | 단점 |
|---|---|---|---|
| **A** | `.com`/`.io` 신규 구매 + Resend | 발신 주소가 `alerts@<도메인>`. 스팸 위험 최저 | 연 1~2만 원. 결제·소유 주체를 정해야 함 |
| **B** | SendGrid 단일 발신자로 먼저 시작 | 도메인 불필요, 즉시 착수 | 발신자가 **개인 주소로 보임**. 하루 100통 한도 |
| **C** | 팀원 보유 도메인의 서브도메인 (잠정, 가능하면) | 비용 0, A와 품질 동일 | 그 팀원 계정에 묶임. 졸업 후 인계 필요 |

**(잠정 결정) C가 가능하면 C, 아니면 A.** B는 폴백으로만 — 나중에 도메인으로 옮겨도 구독
레코드 스키마(§6-1)는 그대로 쓸 수 있어 이전 비용이 작다.

**가장 먼저 해야 하는 이유** — 새 도메인은 발신 이력이 없어 초기에 스팸 분류 위험이
크다(§8-4). 일찍 붙여둘수록 평판이 쌓인다.

**함께 정할 것** — 프로젝트 종료 후 도메인 처리(갱신/해지).

### A-2. Cloudflare 계정 주체

구독 접수 엔드포인트(Worker)와 구독자 저장소(KV)가 필요하다. 무료 티어로 충분하고
상시 서버는 필요 없다 — 발송은 기존 GitHub Actions 크론에서 한다.

**여기가 개인정보가 실제로 놓이는 유일한 장소다.** 리포는 PUBLIC 이라 구독자 이메일을
절대 커밋하지 않기로 되어 있어(§6-3 ★), 이메일 주소는 KV 에만 존재한다.
즉 **그 계정 접근권 = 개인정보 접근권**이다.

| | 선택지 | 장점 | 단점 |
|---|---|---|---|
| **A** | 팀 공용 구글 계정으로 Cloudflare 가입 (잠정) | 개인 계정에 개인정보가 안 묶임. 인계·삭제가 깔끔 | 계정 하나 더 관리 |
| **B** | 팀원 개인 계정 + 팀 공유 | 즉시 가능 | 그 사람이 개인정보 보관 책임을 짐. 졸업 시 이전 필요 |
| **C** | Cloudflare 안 쓰고 구글 폼 + 스프레드시트 | 팀이 이미 쓰는 도구. 학습 비용 0 | 시트에 이메일이 쌓이는 건 동일. 수신거부 링크를 직접 못 만듦 |

**(잠정 결정) A.** C는 수신거부 원클릭(§6-3)이 안 된다는 게 결정적이다 — 더블 옵트인을
생략한 대가로 그걸 보장하기로 했는데, 그 방어가 사라진다.

**함께 정할 것** — 프로젝트 종료 시 전량 삭제를 누가 확인하는가.

### A-3. 구독 UI 위치

| | 선택지 | 장점 | 단점 |
|---|---|---|---|
| **A** | 홈 하단 | 가장 많이 노출 | 홈이 이미 길다 |
| **B** | 신호 탭 안 (잠정) | 맥락이 맞음 — 신호를 보다가 구독 | 탭에 안 들어가면 못 봄 |
| **C** | 별도 페이지 | 안내문을 충분히 넣을 수 있음 | 한 단계 더 들어가야 함 |
| **D** | 홈 하단 + 신호 탭 둘 다 | 노출 최대 | 폼이 두 군데면 관리 지점이 둘 |

**(잠정 결정) B.** 알림이 신호를 전달하는 기능이므로 신호를 보고 있는 사람이 가장 자연스러운
구독자다. 노출이 부족하면 나중에 D로 늘리면 된다.

**함께 정할 것** — 수집 안내문(수집 항목·목적·보관기간)을 누가 쓰는가.
이름·소속은 받지 않고 이메일 주소 하나만 받는다.

## B. 발송 품질 — 안 정하면 구독자가 스팸을 받는다

### B-1. θ 재보정 시점

`COMBINED_THRESHOLDS.theta_shift = 0.95` 는 **2000–2021 월별** 결합 지수(std≈0.80)의
p85 인데, 알림이 실제로 도는 계열은 **일별**(std 1.85)이다. 문턱을 2.3배 넓은 분포에
대고 있어서 발동률이 설계 의도 15% 가 아니라 **67%(40/60일)** 다.

**⚠️ 가 이틀에 한 번 뜨는 건 뉴스가 시끄러워서가 아니라 문턱이 낮아서다.**

| | 선택지 | 근거 |
|---|---|---|
| **A** | 백필 완료 직후 (잠정) | 백필이 2021-06~2026-06 을 채우면 일별 5년치라 p85 가 충분히 안정된다 |
| **B** | 백필 + 4주 더 | 더 안전하지만 그만큼 ⚠️ 를 못 연다 |
| **C** | 지금 두 달치로 잠정 재보정 | 빠르지만 나중에 또 바꿔야 하고, **경계일이 둘이 되어 평가 구간이 쪼개진다** |

**(잠정 결정) A.** C의 대가가 크다 — 아래 비소급 방침 때문에 θ 를 바꿀 때마다 경계일이
하나씩 생기고, 알림 평가 구간이 그만큼 잘린다.

> **소급 재계산은 하지 않기로 확정했다 (2026-09-02).** 새 θ 는 경계일 이후에만
> 적용하고 과거 등급은 손대지 않는다. 이유 다섯은 `notification_design.md` §9
> 「방침 결정 — θ 재보정분을 과거로 소급하지 않는다」에 있다. 요약: ① 「과거 실시간
> 값을 덮어쓰지 않는다」 원칙 ② 소급하면 사전 등록이 무너짐 ③ 백필 전 지수가 남아
> 있지 않아 재현 불가 ④ 표본을 늘려도 검정력이 안 생김 ⑤ 발송 로그와 신호 기록이 어긋남.

### B-2. 기본 발동 등급 — 🔴 vs ⚠️

연속 일별 구간 2026-08-11~09-01(20 거래일) 기준. 등급은 🔴 1 · ⚠️ 8 · 🟢 2 · ⚪ 9 이고
**⚠️ 8건은 전부 `tone_shift` 단독**이다.

| | 선택지 | 발동 빈도 | 귀무가설 | 판단 |
|---|---|---|---|---|
| **A** | 🔴 만 (현행 유지) (잠정 — 지금) | 1회 ≈ 월 1~2회 | 22.4% | 헛경보 최소. 표본이 안 쌓여 검증은 사실상 불가 |
| **B** | θ 재보정 후 ⚠️ 로 낮춤 (잠정 — 재보정 후) | 재보정 시 20일에 3회 | 14.4% | 표본이 늘고 귀무가설도 낮아 검정력이 낫다 |
| **C** | 지금부터 ⚠️ | 9회 ≈ 2.2일에 1회 | 14.4% | θ 미보정 상태라 스팸이 된다 |

**(잠정 결정) 지금은 A, θ 재보정 후 B로 전환.** 이 항목은 지금 결론을 낼 필요가 없다 —
B-1 이 끝나면 자동으로 다시 올라온다.

**⚠️ 주의 — 두 티어는 귀무가설이 다르다.** 🔴 은 `divergence`(\|S&P\| ≥ 0.80% 조건)라
22.4%, ⚠️ 의 `tone_shift` 는 시장 조건이 없어 14.4% 다. **보고서에서 두 티어의 적중률을
합산하거나 같은 기준과 비교하면 안 된다.**

### B-3. 게이트 임계값(기사 15건 · CI 폭 0.60) 보정 시점

이 값은 **데이터로 정한 값이 아니다.** 코드에도 "잠정"이라 적혀 있고, 다른 θ 는 전부
분위수로 보정했는데 이것만 안 됐다. 알림이 이 게이트에 직접 의존한다 — ⚠️/🔴 을
⚪ 관망으로 낮추면 발송이 금지되므로 **헛경보를 막는 마지막 방어선**이다.

| | 선택지 | 근거 |
|---|---|---|
| **A** | 수집 정상화 4주 후 (잠정) | 수집이 깨져 있던 기간만 빼면 된다. 요금제와 무관하다(위 정정) |
| **B** | Basic 전환 후 4주 | ~~요금제 분포를 맞춘다~~ — 전제가 틀려 폐기. 이유 없이 늦춰질 뿐이다 |
| **C** | 현행 유지 | 지금도 동작은 하지만 근거가 없다 |

**(잠정 결정) A.** 요금제와 무관하다는 것이 확인됐으므로(위 정정) D-4 를 기다릴 이유가
없다. **필요한 건 깨끗한 수집 4주뿐이다.** 9/2 판에서 B 로 미뤄뒀던 것을 되돌린다 —
이 항목은 원래 일정으로 돌아온다.

**참고** — 게이트는 `1066adf`(2026-08-24)에서 배선된 뒤 지금까지 한 번도 발동하지
않았다. 버그가 아니라 그 6일이 전부 기사 21~112건 · CI 폭 0.42~0.43 으로 통과 조건을
만족했기 때문이다. 커버리지가 6일뿐이라는 뜻이기도 하다.

### B-4. 게이트 판정 기준

조교님 답변(`docs/ta_feedback_2026-08.md` 질문 5)은 **"A안(게이팅)·B안(표시)의 절충 —
측정은 그대로 두고 경보만 게이팅"** 이고 **판정 기준 자체는 지정하지 않으셨다.**
"CI 가 0을 크게 걸침"은 문제 상황 서술이지 결정된 규칙이 아니다. 구현이 `폭 0.60` 을
골랐는데 **왜 폭 기준인지가 어디에도 없다.**

| | 선택지 | 뜻 | 판단 |
|---|---|---|---|
| **A** | 폭 0.60 단독 유지 + 근거를 분위수로 재산출해 문서화 | "기사 간 어조가 엇갈린다" | 크기 신호에는 맞지만 부호 신호의 전제를 못 지킴 |
| **B** | 폭 유지 + `divergence` 계열에만 0 포함 검사 추가 (잠정) | 신호 성격에 맞춰 분리 | 팀원 제안. 과잉 억제 없이 부호 전제를 지킴 |
| **C** | 0 포함 검사로 전면 교체 | "뉴스가 긍정인지 부정인지 말할 수 없다" | 경보일 9일 → 3일. **과잉 억제** |

**(잠정 결정) B.** `tone_shift`(급변)는 크기 신호라 지수가 0을 걸쳐도 "많이 변했다"는 주장이
성립한다. 반면 `divergence`("뉴스는 긍정인데 시장은 하락")는 뉴스가 긍정임을 말할 수
있어야 성립하므로 0 포함 검사가 필요하다.

**참고 측정** — 전면 적용(C)은 9일 → 3일, 부호 신호에만(B)은 9일 → 9일이며 7/17 하나가
🔴 → ⚠️ 로 내려간다.
⚠️ 이 수치는 `outputs/news_index_live.csv` 60일을 **재채점한 시뮬레이션**이고 실제 발송
기록(`daily_signals.csv` 24행)과는 다른 표본이다. 두 표본을 섞어 인용하면 안 된다.

**B-3 과 같이 처리하는 것이 자연스럽다** — 어차피 같은 함수(`news_signals.confident()`)를
건드리고, 경계일도 하나로 맞출 수 있다.

> **사전 등록 주의.** 이 항목만은 잠정 결정의 성격이 다르다. **기준을 결과보다 먼저
> 박아야** 의미가 있다 — 나중에 적중률을 보고 고치면 사전 등록이 깨진다. 그래서
> 9/8 확정과 동시에 근거를 `notification_design.md` §9 결정 이력에 날짜와 함께 남기고,
> 이후 변경은 경계일을 기록해 소급 없이 적용한다.

## C. 지도교수님 · 조교님 확인

### C-2. 적중률 유의성 한계를 어떻게 공유할 것인가

조건부 귀무가설(§7-7)을 계산해보니 기본 채널(🔴)의 기저가 **22.4%** 였다. 알림이
"이미 시장이 크게 움직인 날"에만 나가기 때문이다(변동성 군집). 그 결과:

| 알림 수 | 25% 적중 시 p | 유의하려면 |
|---|---|---|
| 20건 (약 1년) | 0.474 | 9건 (45%) |
| 60건 (약 2.5년) | 0.359 | 20건 (33%) |
| 800건 (약 30년) | 0.041 | 199건 (25%) |

🔴 이 월 1~2회니 **800건이면 30년**이다. 관측 25% 로는 어떤 현실적 기간에도 유의해지지
않는다. 그래서 §8-1 을 고쳐 "적중률로 성능을 입증한다"는 목표를 접고 ① 기준을 사전
등록했다 ② 적중률을 조건부 기저와 나란히 보고한다 — 여기까지만 주장하기로 했다.

| | 선택지 | 판단 |
|---|---|---|
| **A** | 다음 미팅에서 먼저 말씀드림 (잠정) | 기대치를 미리 맞춘다. "적중률 결과"를 기대하고 계시면 나중에 곤란해진다 |
| **B** | 보고서 한계 절에만 적음 | 지금 부담이 없지만, 발표 때 처음 나오면 방어적으로 보인다 |
| **C** | 문서 링크만 드리고 질문이 오면 설명 | 중간. 다만 §8-1 이 이미 공개 리포에 있어 어차피 보시게 된다 |

**(잠정 결정) A.** 나쁜 소식이지만 **우리가 스스로 두 번 잡아낸** 것이다 — 10%→14.4% 는
문서에 "계산해봐야 안다"고 미리 적어둔 덕에, 14.4%→22.4% 는 팀 검토에서 잡혔다.
안 잡았으면 보고서에 "무작위의 1.7배"가 들어갔을 것이다(조건부로는 1.1배).
**방법론적으로는 오히려 강점으로 읽힐 수 있는 종류의 이야기다.**

### C-3. 교수님 확인을 어떤 묶음으로 받을 것인가

두 가지가 걸려 있다.

**(a) 발동 기준·적중 정의는 확인 전이다.** 조교님 질문 1 의 "알림 단계까지 확장해도
되는가 → 좋은 확장"은 **확장 여부**에 대한 답이다. §2 발동 기준(🔴 기본, θ 값들)과
§7 적중 정의(분위수 상위 10%, 양측, 1거래일)는 확인받지 않았고, 설계 문서 첫 줄에
그렇게 명시해 두었다. 확인이 붙으면 사전 등록이 "우리끼리 정하고 우리끼리 지켰다"가
아니게 되어 방법론 절에서 무게가 달라진다.

**(b) VIX.** 교수님께서 VIX 사용을 보류시키셨고 사유는 전달받지 못했다. 팀 방침은
빅스 기준 유지로 정했지만, 알림 쪽에 걸린 곳이 있다.

| 어디 | VIX 의존 | 빼야 한다면 |
|---|---|---|
| **적중 판정식** (사전 등록·고정) | \|ΔVIX\| > 2.401pt, S&P 와 **합집합** | 귀무가설 14.4% → 10%. 고정한 JSON 재생성 |
| ⚠️ `tone_vs_vix` | \|ΔVIX\| ≥ 1.00pt | 신호 하나 제거 |
| 🔴 `divergence` (기본 채널) | **없음 — S&P 만** | 영향 없음 |

🔴 발동 자체는 VIX 와 무관한데 **적중 판정이 걸린다.** 그리고 타이밍이 전부다 —
**알림을 켜기 전에 바꾸면** 사전 등록을 더 엄밀하게 만든 정정이지만, **켠 뒤에 바꾸면**
사후 조정이 된다. 지금은 한 건도 안 보냈으니 바꿀 수 있는 마지막 구간이다.

| | 선택지 | 판단 |
|---|---|---|
| **A** | VIX + 알림 기준을 한 번에 여쭙기 (잠정) | Fed 축 가중치 1:1:1 근거도 VIX 상관 위에 있어 같은 뿌리다. 워크스페이스 "여쭐 것 1"에 얹으면 된다 |
| **B** | VIX 만 먼저, 알림 기준은 나중 | VIX 답이 급하긴 하나, 두 번 여쭙게 된다 |
| **C** | 팀 판단대로 진행, 확인은 최종 발표 때 | 사전 등록의 무게가 약해지고, VIX 를 빼야 할 경우 이미 늦다 |

**(잠정 결정) A.** 답변을 받는 데 시간이 걸리는데 **답이 늦으면 알림을 못 켠다.**
A-1(도메인)만큼 일찍 물어야 하는 이유다.

## D. 운영

### D-1. 발송 시각과 크론 구조

현재 크론 하나. `.github/workflows/daily-news.yml`, `0 22 * * *` (=07:00 KST, 미 증시
마감 후). FOMC 문서는 전부 미 동부 14:00 공개 = KST 새벽 3~4시라 4시간 시차가 있다.

| | 선택지 | 판단 |
|---|---|---|
| **A** | 아침 07:00 하나 (현행 유지) (잠정 — 1단계) | 크론 추가 없이 바로 켤 수 있다. 발표 후 4시간 침묵이 대가 |
| **B** | 아침 + FOMC 새벽 (잠정 — 확장 시) | 연 8회만 새벽에 더 돈다. `overnight` 필드로 구독자가 거부 가능 |
| **C** | 설계대로 셋 (예고 + 새벽 + 아침) | 가장 완전하지만 크론 둘을 새로 만들어야 하고 예고는 D-2 에 막혀 있다 |

**(잠정 결정) 1단계는 A, 인프라가 안정되면 B.** C 의 "전날 예고"는 FOMC 일정 소스가 있어야
가능한데 그게 D-2 다.

**주의** — 회의록은 "예정일"과 "실제 도착"이 어긋난다(2026-08-03 회의 회의록은 3주 뒤인
8/25 에도 미도착). **예고는 일정 기준, 결과 알림은 실제 도착 기준**이어야 한다.

### D-2. FOMC 일정 소스

§2-2 는 성명문·기자회견·회의록 공개를 캘린더성 알림으로 보낸다고 설계돼 있는데,
**그 일정을 담은 데이터 소스가 리포에 없다.**

| | 선택지 | 장점 | 단점 |
|---|---|---|---|
| **A** | 수기 CSV (연 8회 직접 입력) (잠정 — 나중) | 즉시 가능, 의존성 0 | 매년 갱신. 빠뜨리면 조용히 실패 |
| **B** | 연준 사이트 크롤링 | 자동 | 페이지 구조 변경에 취약. 만들 게 하나 더 |
| **C** | 일정 알림을 1단계에서 제외 (잠정 — 지금) | 나머지 알림에 영향 없음 | "조용한 달에도 빈 채널이 안 된다"는 §2-2 의 이점을 포기 |

**(잠정 결정) 지금은 C, 나중에 A.** 일정 알림은 신호 알림과 독립이라 빼도 아무것도 안
깨진다. 넣을 때는 연 8회짜리라 수기 CSV 로 충분하다.

### D-3. 발송 로그를 공개 리포에 커밋하는 것

`outputs/notification_log.csv` 가 매일 1행씩(억제된 날 포함) 쌓이고 deploy 봇 커밋에
묻어 공개 리포에 올라간다. 이미 그렇게 구현·동작 중이다.

| | 선택지 | 판단 |
|---|---|---|
| **A** | 공개 커밋 유지 (잠정) | **사전 등록의 연장** — 커밋 타임스탬프가 남아 사후 체리피킹이 불가능. 조교님·교수님이 리포만 보고 검증 가능 |
| **B** | 비공개(gitignore) | 개인정보 위험 0. 대신 "언제 무엇을 보냈나"의 외부 증거가 사라진다 |
| **C** | 드라이런은 빼고 실제 발송분만 커밋 | 로그가 깔끔. 대신 **θ 재보정 전후 발송량 비교 자료가 사라진다** |

**(잠정 결정) A.** 공개 히스토리는 영구라 위험이 실재하지만, 이미 코드로 막아뒀다 —
구독자 식별 정보를 어떤 컬럼에도 두지 않고(수신자는 '수' 하나), `suppressed_reason` 을
자유 문자열이 아닌 **고정 코드 6개**로 제한했으며, 컬럼 집합을
`tests/test_notifier.py::test_log_schema_is_locked` 가 잠근다.

### D-4. 뉴스 API 요금제 다운그레이드 시점

| 요금제 | 월 | 요청당 기사 | 일 요청 |
|---|---|---|---|
| Basic | $29 | 20건 | 2,500 |
| **Standard (현재)** | $49 | 50건 | 10,000 |

| | 선택지 | 판단 |
|---|---|---|
| **A** | 백필 끝나면 즉시 Basic | 월 $20 절감. 단 코드 두 곳을 고쳐야 한다(아래) |
| **B** | 보정이 끝날 때까지 Standard 유지 | 보정이 요금제와 무관해져 **조건이 의미를 잃었다.** C 와 실질적으로 같다 |
| **C** | 계속 Standard (잠정 — 팀 의견) | 코드 변경 0. 백필·재수집 여지와 폭증일 여유를 월 $20 로 산다 |

**(잠정 결정) C — 팀 의견을 반영해 A 에서 바꿨다 (2026-09-05).**

9/2 판의 A 는 "Basic 으로 내려야 B-3 을 제대로 보정한다"를 근거로 삼았는데 **그 근거가
틀렸다**(위 정정). 남은 것은 순수한 비용 대 여유의 문제이고, 그 저울에서는 Standard 가
불합리하지 않다.

| Basic 으로 내리면 | 영향 |
|---|---|
| 일일 수집 기사 수 | **변화 없음** — 전수 회수라 요금제와 무관 |
| 게이트·θ 보정 | **변화 없음** — B-3 은 요금제와 독립 |
| 백필 속도 | **약 10배 느려짐** — 요청당 50→20건(2.5배) × 일 한도 10,000→2,500(4배) |
| 폭증일 여유 | 상한 2,000건 → 800건. FOMC·잭슨홀에 풀이 800 을 넘으면 잘린다 |
| 코드 | `engine/news_scrape.py:49` `PER_PAGE = 50` → 20, 그리고 `pages` 상향 필요 |

**백필이 도는 동안 Standard 를 유지해야 한다는 것에는 이견이 없다.** 실제 쟁점은
백필이 끝난 뒤 월 $20 을 계속 낼지인데, 이건 **재수집 계획이 더 있느냐**에 달렸다 —
있으면 Standard 가 값을 하고, 없으면 코드 두 줄 고치고 내리면 된다. 지금은 팀 의견대로
C 로 두고, 백필 완료 시점에 다시 본다.

## 이미 확정된 것 — 재논의 방지

전부 `notification_design.md` §9 결정 이력에 근거가 있다.

| 항목 | 결정 | 버린 것과 이유 |
|---|---|---|
| 채널 | **이메일** (푸시는 설계만) | 웹푸시 — FOMC 발표가 KST 새벽 3~4시인데 그 시각 데스크톱은 꺼져 있고 아이폰은 PWA 추가를 안 거침 |
| 개인정보 | 주소 하나만 | 더블 옵트인 — 학부 프로젝트에 과함. 원클릭 수신거부로 상쇄 |
| 적중 정의 | 분위수 상위 10%, 양측, 1거래일 | 절대 수치(S&P −1%) — 하위 17% 수준이라 무작위로도 6일 중 1일 적중 |
| 발송 서비스 | Resend + 자체 도메인 | Gmail SMTP — 개인 계정 보안·스팸 위험 |
| 정정 알림 | 등급이 실제로 바뀐 경우만 | 모든 확정판 전환 — 연 8회 "바뀐 게 없음" 알림 |
| 귀무가설 | 신호별 조건부 (🔴 22.4% / ⚠️ 14.4%) | 무조건부 14.4% 단일 — 알림은 아무 날에나 안 나감 |
| θ 재보정 소급 | **하지 않음** (경계일 이후만) | 소급 재계산 — §9 방침 결정에 이유 5가지 |
| VIX | 사용 유지 | — (교수님 확인은 C-3 에서 함께) |

> **정정 알림은 이미 실제 사례가 있다.** 2026-07-29 는 회의록 도착 후
> 🔴 경고 → 🟢 정합 으로 뒤집혔다(확정 2026-08-29). 기록상 🔴 두 건 중 하나다.
