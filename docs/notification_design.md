## 1. 목적과 범위

**목적**: 조용한 숫자를 능동적으로 전달한다. 지금은 사용자가 사이트에 들어와야만
신호를 볼 수 있다. 파이프라인에 Notifier 단계를 두어 에이전트가 스스로 알린다.

**범위 — 이메일로 구현한다. 웹푸시는 설계만 남기고 구현하지 않는다.**

| 환경 | 웹푸시 실제 동작 | 이메일 |
|---|---|---|
| 안드로이드 Chrome | 알림 표시줄. Chrome 종료 상태에서도 도착 | 도착 |
| Windows·Mac 데스크톱 | OS 알림. **브라우저가 완전히 종료돼 있으면 그 시점엔 못 받는다** | 도착 |
| iPhone·iPad | **"홈 화면에 추가"(PWA)를 먼저 해야만 작동** | 도착 |
| 진입 마찰 | 브라우저 권한 팝업(거부율 높음) | 주소 입력 |
| 도달 실패 양상 | 권한 거부 · 구독 만료 | 스팸함 |

웹푸시를 미룬 이유는 **가장 실시간성이 필요한 시각에 가장 안 닿기 때문**이다.
FOMC 발표는 KST 새벽 3~4시인데, 그 시각 데스크톱은 꺼져 있고 아이폰 사용자는
홈 화면 추가 단계를 대부분 거치지 않는다. Service Worker · VAPID · PWA 안내를
만드는 비용 대비 도달이 불확실하다.

**다만 구조는 확장 가능하게 둔다.** 구독 레코드에 `channel` 필드를 처음부터 두고
(§6-1), 발송 로그도 채널별로 남긴다(§7-1). 나중에 푸시를 얹을 때 스키마를 바꾸지
않아도 된다. **확장하더라도 한 사람 = 한 채널**로 유지한다 — 같은 알림이 두 번
가고 수신자 수가 중복 집계되면 §7의 적중 평가가 지저분해진다.

**개인정보는 최소 수준으로 받는다.** 이메일 주소 하나만 받고 이름·소속은 받지
않는다. 구독 폼에 수집목적·보관기간을 안내하고, 모든 메일 하단에 원클릭 수신거부
링크를 넣는다(§6-3).

**상시 서버는 필요 없다.** 발송은 기존 GitHub Actions 크론에서 한다. 필요한 건
① 구독 접수 엔드포인트 ② 구독자 저장소 ③ 이메일 발송 서비스 셋이다(§6).

## 2. 발동 기준

### 2-1. 기본값

**🔴 경고 + Fed 공식 일정.** 구독자가 ⚠️ 주의 이상으로 낮출 수 있다.

기본값을 🔴로 둔 근거는 실측 빈도다. `outputs/daily_signals.csv` 의 연속 일별 구간
2026-08-11~09-01(20 거래일):

| 기준 | 발동 횟수 | 환산 | 초판(8/11~08-25, 15일) |
|---|---|---|---|
| ⚠️ 이상 전부 | 9번 | 2.2일에 한 번 | 7번 |
| ⚠️ 이상, 진입 시점만 | 5번 | 주 2회 | 4번 |
| **🔴만** | **1번** | **월 1~2회** | 1번 |

20일의 등급은 🔴 1 · ⚠️ 8 · 🟢 2 · ⚪ 9 이고, **⚠️ 8건은 전부 `tone_shift` 단독
발동**이다. 표본을 5일 늘려도 그림이 그대로다 — 🔴 은 여전히 8/20 하나뿐이고
⚠️ 는 여전히 한 신호에서만 나온다.

**다만 초판의 원인 진단은 틀렸다.** 초판은 ⚠️ 홍수의 원인을 "표본 적은 뉴스가
흔들렸다"(하루 3~12건)로 봤다. 재측정해보니 원인은 표본 크기가 아니라 **θ 척도
불일치**다.

`analysis/signals.py` 의 `COMBINED_THRESHOLDS` 는 `theta_shift=0.95` 인데, 주석대로
"2000-2021 **월별** 결합 지수의 p85"다. 그 월별 계열은 std≈0.80 이다. 그런데 알림이
실제로 도는 계열은 **일별** 결합 지수(`outputs/daily_headline.csv`, 2026-07-03~09-01
61일)이고 여기 std 는 **1.85**, 범위는 **−7.08~+4.35** 다. 같은 문턱을 2.3배 넓은
분포에 대고 있다.

| | 설계상의 정의 | 월별 척도(현행) | 일별 실측 |
|---|---|---|---|
| `theta_shift` | p85 \|Δ결합\| = 상위 15%만 발동 | 0.95 | **3.28** |
| `theta_t` | p25 \|결합\| = 하위 25%만 차단 | 0.22 | 0.55 |

현행 0.95 의 실제 발동률은 **67%(40/60일)** 다 — 설계 의도 15% 의 4.5배다.
θ_shift 를 일별 p85(3.28)로 재보정하면 **9/60일 = 15%** 로 설계값에 복귀한다.
즉 **⚠️ 가 이틀에 한 번 뜨는 건 뉴스가 시끄러워서가 아니라 문턱이 낮아서다.**

(실제 기록상 tone_shift 발동은 20일 중 9일 = 45% 로 위 67% 보다 낮다. 두 수치가
다른 이유는 §8-2b — 기록은 뉴스 백필 이전 지수로 생겼다. 어느 쪽이든 15% 는 아니다.)

반면 유일한 🔴(8/20)은 `tone_shift;divergence;tone_vs_vix` **세 신호가 동시에** 터진
날이고, `divergence`·`tone_vs_vix` 는 θ 척도와 무관한 **시장 조건**을 따로 건다(§7-7).
그래서 θ 재보정 전에도 🔴 은 기준으로 삼을 만하다.

**🔴 기본값은 유지한다. 다만 근거가 바뀌었다** — "⚠️ 가 표본 탓에 시끄럽다"가 아니라
**"⚠️ 의 유일한 신호인 tone_shift 의 문턱이 아직 미보정"** 이기 때문이다. θ 재보정이
끝나면 ⚠️ 는 20일에 3번 수준으로 내려가므로, 그때 기본값을 ⚠️ 로 낮출지 재검토한다(§10).

**주의: 표본이 20일이다.** 위 빈도는 여전히 근거가 얇다. 이 기준은 잠정이며, 데이터가
쌓이면 재측정한다(`news_signals.Thresholds` 주석의 "임계값 잠정" 원칙과 같다).

### 2-2. Fed 공식 일정

성명문 발표 · 기자회견 · 회의록 공개. 신호가 아니라 캘린더성 알림이므로 등급 기준과
독립적으로 발송한다. 연 8회라 피로가 없고, 조용한 달에도 빈 채널이 안 된다.

### 2-3. 정정 알림

**`grade_final` 이 `grade` 와 다를 때만 발송한다.**

질문 6 절충안(속보치/확정판 이원화) 때문에 회의록이 3주 뒤 도착하면 과거 등급이
바뀔 수 있다. 등급이 실제로 달라진 경우에만 알린다 — 연 1~2회 수준이라 소음이
거의 없고, **"과거 실시간 값을 덮어쓰지 않고 정정한다"는 원칙이 사용자 눈에 보이는
유일한 지점**이다.

등급이 그대로인 확정판 전환은 알리지 않는다. 연 8회씩 "바뀐 게 없음" 알림이 가는
셈이라 피로 대비 가치가 낮다.

## 3. 발송 시각

FOMC 관련 문서는 전부 **미 동부 14:00 공개 = KST 새벽 3~4시**다. 기존 파이프라인은
07:00 KST 하루 한 번이라 4시간 시차가 있다.

**기본은 새벽 실시간, 구독자가 거부하면 예고+아침으로 폴백한다.**

| 구독 설정 | 동작 |
|---|---|
| `overnight = true` (기본) | FOMC 당일 새벽 3~4시 실시간 발송 |
| `overnight = false` | FOMC 전날 저녁 "내일 새벽 발표 예정" 예고 → 아침 07:00 결과 |
| 일반 신호 알림 | 설정과 무관하게 매일 07:00 배치 |

크론이 셋으로 갈린다: 전날 저녁 예고 / FOMC 새벽 / 매일 아침.

**이메일에서 `overnight` 의 의미**: 이메일은 사람을 깨우지 않고 받은편지함에 쌓일
뿐이므로, 새벽 발송의 부담이 작다. 그래도 설정은 남긴다 — 새벽 메일 자체를 원치
않는 사람이 있고, 나중에 푸시를 얹으면(§1) 그때 의미가 커진다.

**주의**: 회의록은 "예정일"과 "실제 도착"이 어긋난다. 2026-08-03 회의 회의록은 3주가
지난 8/25 시점에도 도착하지 않았다(`outputs/vintage_meetings.csv`). 예고는 일정
기준으로, 결과 알림은 **실제 도착 기준**으로 발송해야 한다.

## 4. 억제 조건 — 안 울려야 할 때

| 조건 | 이유 |
|---|---|
| **⚪ 관망이면 발송 금지** | 질문 5의 A+B 절충안을 알림에도 그대로 적용. 이미 등급이 관망이면 🔴/⚠️가 아니라 자동으로 걸러지지만 명시해둔다 |
| **수집 실패일** | API 402·네트워크 오류로 기사 0건인 날 |
| **소급 발송 금지** | 과거 재계산이 오늘 알림을 만들면 안 된다. 발송 대상은 항상 당일 |
| **회의 사이 구간 — 억제하지 않되 표기 구분** | Fed 축이 상수인 기간의 tone_shift 는 전부 뉴스축 움직임이다. "Fed 톤 변화"가 아니라 **"뉴스 감성 변화"**로 적는다 |
| 시장 휴장일 | divergence 계열 신호는 시장 데이터가 없으면 발동하지 않으므로 자동 처리됨 |

## 5. 알림 내용 규격

포함:
- 등급 + 한 줄 이유(발동 신호의 detail)
- **신뢰도 높음/보통/낮음** — 질문 3 피드백과 같은 원칙. 숫자는 노출하지 않는다
- **"참고용·투자조언 아님"** — 금융 알림은 특히 조언처럼 읽힌다
- **"회의록 반영 전 잠정"** (속보치인 경우)
- 링크: Signals 페이지의 해당 날짜

제외:
- 지수 값·CI 폭·기사 수 등 숫자 일체 → 상세보기(사이트)에서만
- 방향 전망·투자 판단

**이메일 요건**
- 본문 하단에 **원클릭 수신거부 링크** 필수(§6-3)
- **제목에 등급을 넣는다** — 받은편지함에서 열지 않고도 판단할 수 있어야 한다
- **공간이 남는다고 숫자를 넣지 않는다.** 위 규격을 그대로 지킨다 — 이메일만
  상세해지면 사이트의 "상세보기" 구분(질문 3 피드백)이 무너진다

신뢰도 등급은 `dashboard-web/src/lib/data.js` 의 `confidenceLevel()` 과 **같은 규칙**을
쓴다(기사 15건, CI 폭 0.60). 알림과 사이트가 다른 말을 하면 안 된다.

## 6. 인프라

```
[사이트] 구독 폼 ──▶ Cloudflare Worker ──▶ KV (구독자 저장)
                          ▲                    │
              수신거부 링크 ┘                   │
                                               │
[GitHub Actions 크론] ──── 발송 시 읽기 ───────┘
        └──▶ 이메일 발송 서비스 ──▶ 받은편지함   (channel = email)

        ( 확장 시: └──▶ pywebpush ──▶ 브라우저   channel = push )
```

### 6-1. 구독 레코드

```json
{
  "id":          "uuid",
  "channel":     "email",
  "email":       "someone@example.com",
  "level":       "alert",
  "fed_events":  true,
  "overnight":   true,
  "created_at":  "2026-08-26T00:00:00Z",
  "unsub_token": "..."
}
```

- `channel` — 지금은 `email` 만 쓴다. 확장 시 `push` 가 추가되고 그때는
  `endpoint`·`keys` 필드를 채운다. **한 사람이 둘 다는 없다**(§1)
- `level` — `alert`(🔴만) 또는 `caution`(⚠️ 이상)
- `unsub_token` — 수신거부 링크용 난수. **이메일 구독에 필수**

`channel` 을 지금 넣어두는 이유는 나중에 푸시를 얹을 때 저장된 레코드를 마이그레이션
하지 않기 위해서다. 필드 하나 비용으로 확장 경로를 열어둔다.

### 6-2. 발송 서비스 — Resend + 자체 도메인

| 방식 | 한도 | 도메인 | 판단 |
|---|---|---|---|
| **Resend** | 3,000/월 · 100/일 | 필요 | **채택.** SPF/DKIM 정렬이 되어 스팸함 위험이 가장 낮고, 발신 주소를 `alerts@<도메인>` 으로 둘 수 있다 |
| SendGrid 단일 발신자 검증 | 100/일 | 불필요 | 도메인이 늦어질 때의 대안. 발신자가 개인 주소로 보인다 |
| Gmail SMTP (앱 비밀번호) | 500/일 | 불필요 | 스팸 분류 위험 + 개인 계정 보안 부담 |

사이트는 `aicp-econpilot.github.io` 이지만 **메일 발송용 도메인은 별도로 확보한다.**
사이트 도메인과 같을 필요는 없다.

구독자 규모상 한도는 문제가 아니다. **도메인 확보가 지연되면 SendGrid 단일 발신자로
시작하고 나중에 옮긴다** — 구독 레코드(§6-1)는 그대로 쓸 수 있어 이전 비용이 작다.

API 키는 **GitHub Actions Secret** 에 둔다. 리포에 넣지 않는다
(`docs/TEAM_GUIDE.md` §5 의 키 취급 원칙과 동일).

### 6-3. 수신거부와 개인정보 (최소 수준)

- **구독 폼 안내문** — 수집 항목(이메일 주소), 목적(알림 발송), 보관기간
- **모든 메일 하단에 원클릭 수신거부 링크** — `?token=<unsub_token>`.
  `List-Unsubscribe` 헤더도 함께 넣는다
- **수신거부 시 레코드 즉시 삭제.** 보관하지 않는다
- **프로젝트 종료 시 전량 삭제**
- 이름·소속 등 **추가 정보는 받지 않는다**

더블 옵트인(확인 메일)은 하지 않는다. 타인 주소 무단 등록을 막는 정석이지만,
확인 플로우를 더 만들어야 하고 학부 프로젝트 규모에는 과하다. **대신 수신거부를
한 번 클릭으로 끝나게 해 오등록 피해를 최소화한다.**

### ★ 구독 정보는 리포에 절대 커밋하지 않는다

리포가 **PUBLIC**이다. 이유가 채널마다 다르고 둘 다 심각하다.

- **푸시 endpoint 가 공개되면** 누구나 그 사람 브라우저로 푸시를 보낼 수 있다
- **이메일 주소가 공개되면** 개인정보 유출이고, 공개 리포는 되돌려도 히스토리에 남는다

이 프로젝트는 데이터를 전부 리포에 커밋하는 구조라 자연스럽게 그 길로 갈 위험이
있어 명시해둔다. 구독자 정보는 KV 에만 둔다.

## 7. 검증 설계 ★

알림을 보냈으면 "그래서 맞았나"를 봐야 한다. 헛경보가 쌓이면 기능 자체가
무의미해지고, **적중 기준을 사후에 정하면 체리피킹**이 된다.

### 7-1. 발송 로그

`outputs/notification_log.csv`

| 컬럼 | 내용 |
|---|---|
| `date` | 발송일 |
| `kind` | signal / fed_event / correction |
| `grade` | 발송 시점 등급 |
| `fired` | 발동 신호 목록 |
| `channel` | email (확장 시 push) |
| `n_recipients` | 해당 채널 발송 대상 수 (개인 식별 정보 없음) |
| `n_failed` | 발송 실패 수 (구독 만료·반송) |
| `suppressed_reason` | 억제된 경우 사유 |

채널별로 한 행씩 남긴다. 한 사람이 한 채널만 구독하므로(§1) 수신자 수는 중복 없이
합산된다.

구독자 개인정보를 담지 않으므로 리포에 커밋해도 안전하다 — **이메일 주소도, 푸시
endpoint 도 이 파일에 들어가지 않는다.** **덮어쓰지 않는다** — 질문 6 원칙의 연장.

### 7-2. 적중 정의 (사전 등록)

**주 기준 — 양측, 1거래일, 상위 10%**

- S&P: 발송일 종가 → 1거래일 뒤 종가의 **|수익률|**
- VIX: 발송일 → 1거래일 뒤의 **|수준 변화(pt)|**
- 둘 중 **하나라도** 전 거래일 분포 상위 10%면 **적중**

**부기준(강건성 확인용)**: 3·5·10거래일. 넷을 다 돌려 좋은 걸 고르면 다중비교이므로,
**주 기준 하나를 미리 못 박고 나머지는 부차적**이라고 선언한다. 조교님께서 질문 4에서
primary/secondary 를 나눈 것과 같은 논리다.

**왜 1거래일인가.** 프로젝트의 기존 분석이 즉각 반응을 본다 — `analyze_alignment.REACTION_OFFSET = 1`, `backtest.N_DAYS = 2`. 적중 기준만 창이 길면 같은 프로젝트가 서로 다른 자를 쓰게 된다. 그리고 divergence 는 "뉴스와 시장이 어긋났다 → 곧 정렬된다"는 신호이므로, **정렬이 빠를수록 신호가 정보를 가졌다는 증거가 강하다.** 창이 길면 무관한 사건이 끼어들 시간이 생겨 적중이 신호의 성능인지 시장의 기본 변동성인지 흐려진다.

창을 늘려도 쉬워지지는 않는다 — 분위수 기준이라 귀무가설이 기간과 무관하게 14.4~14.8% 로 거의 같다. 기간 선택은 난이도가 아니라 **무엇을 주장하는가**의 문제다.

**두 시점만 비교한다.** 발송일 종가와 1거래일 뒤 종가의 차이이며 중간 경로는 보지 않는다.

**네 기간 결과는 항상 함께 싣는다.** 주 기준은 1거래일 하나지만, 보고할 때는
1·3·5·10 네 개의 적중률을 **모두** 표로 낸다. 주 기준이 부진할 때 부기준을 들고 오는
사후 선택을 구조적으로 막기 위해서다. 사전 등록의 실효는 "무엇을 주 기준으로 뒀나"가
아니라 "고르지 못하게 묶어뒀나"에서 나온다.

**측정 창의 시작점은 "발송일 종가"다 — 발송 시각이 아니다.** 일반 신호 알림은
22:00 UTC 크론(=07:00 KST, `.github/workflows/daily-news.yml`)에서 나가고 미 증시
마감은 20:00~21:00 UTC 이므로, **발송 시점에 이미 발송일 종가가 확정돼 있다.**
t 일 종가는 알림 생성에 쓰인 정보이지 예측 대상이 아니며, 판정은 순수하게 t→t+1 이다.
예외는 §3 의 FOMC 새벽 발송(KST 03~04시 = 18~19 UTC)으로, 이때는 당일 미 증시가 아직
열려 있다. **두 경로가 같은 자를 쓰도록 시작점을 종가로 고정한다** — 새벽 발송분은
그날 종가부터 다음 거래일 종가까지를 잰다.

### 7-3. 왜 절대 수치가 아니라 분위수인가

임계값을 절대 수치로 두면 정당화가 필요하다. 실제로 초안에서 "S&P −1%"를 예시로
들었다가 폐기했다 — 리포 시장 데이터 480일(2000-01~2026-08) 분포를 뽑아보니:

```
S&P 수익률 %   5%: -1.97   10%: -1.46   25%: -0.51   50%: +0.05   75%: +0.66   90%: +1.33
VIX 변화(pt)   5%: -2.37   10%: -1.64   25%: -0.72   50%: -0.11   75%: +0.56   90%: +1.48
```

−1%는 대략 **하위 17% 언저리**다. 아무 날이나 찍어도 여섯 번에 한 번은 "적중"한다.
그런 기준으로 나온 적중률은 신호의 성능이 아니라 시장의 기본 변동성이다.

(같은 초안에서 "VIX +10%"도 썼는데, `analysis/collect_market.py` 의 `vix_chg` 는
`vix.diff()` — **포인트 차이**다. % 변화는 파이프라인에 존재하지도 않는다.)

분위수로 정의하면:

1. **임계값을 사람이 고르지 않는다.** 데이터가 정한다. "왜 하필 그 값이냐"가 성립하지 않는다
2. **귀무가설이 계산 가능해진다.** 축 하나만 보면 상위 10% 기준의 무작위 적중률은
   정의상 10%다. 다만 주 기준은 "S&P **또는** VIX"라 실제 귀무가설은 10%가 아니다
   — 실측 **14.4%**(§7-6)
3. 시기별로 분포가 달라져도(2008·2020) 기준이 따라간다

### 7-4. 양측인 이유

🔴 경고의 정체는 `divergence`(뉴스↔시장 괴리)다. **오를지 내릴지 방향을 예측하는
신호가 아니다.** 따라서 변동의 크기만 본다. 단측(악화 방향)은 "경고"라는 단어의
상식적 의미에는 맞지만, 신호 설계가 방향 예측을 목표하지 않는다는 점과 모순된다.

### 7-5. 선행 작업 — 임계값 고정 ✅ 완료 (2026-08-26)

`analysis/hit_thresholds.py` 로 산출해 **고정했다.** 전 거래일 2000-01-03~2026-08-25,
6,701 거래일. 산출물은 `outputs/hit_thresholds.json`(고정값) ·
`docs/alert_hit_thresholds.md`(방법·분포표·강건성).

```
주 기준(1거래일) 적중 판정식
  |S&P 1일 수익률| > 1.78%   또는   |VIX 1일 변화| > 2.40pt
  귀무가설(무작위 날짜의 적중률) = 14.4%
```

부기준: 3일 2.98%/3.93pt(14.6%) · 5일 3.74%/4.76pt(14.5%) · 10일 4.94%/6.00pt(14.8%).

**위기가 만든 값이 아니다.** 2008·2020 을 빼면 1.66%/2.24pt 로 6~7% 낮아질 뿐이고
귀무가설은 14.4% → 14.5% 로 사실상 같다. 조교님 질문 4-4("위기 한두 개가 결과를 만드는지")에 대한 답이
적중 기준 쪽에서도 준비된 셈이다.

**한 번 고정하고 다시 계산하지 않는다.** 재계산하면 사후 조정이 되어 사전 등록의
의미가 사라진다. JSON 에 계산일을 박아두는 것이 그 약속이고, 스크립트도 JSON 이
있으면 `--force` 없이는 덮어쓰기를 거부한다. 문구만 고칠 때는 `--doc-only` 로
고정값을 읽어 문서만 다시 뽑는다.

> **초안의 480일 분포는 폐기했다.** 그건 FOMC 관련일이라 일반 거래일보다 변동이 크다.
> 알림은 아무 날이나 나오므로 위 수치는 **전 거래일** 분포로 다시 뽑은 것이다.

### 7-6. "하나라도" 조건의 실제 귀무가설 — 실측 14.4%

주 기준은 "S&P **또는** VIX 가 상위 10%"이므로 실제 무작위 발생률은 10%가 아니다.
설계 시점에는 "완전 독립이면 19%, 완전 상관이면 10%, 실제로는 그 사이"까지만 말할 수
있었고, §7-5 에서 계산해보니:

| | 무작위 적중률 |
|---|---|
| S&P 단독 초과 | 10.0% |
| VIX 단독 초과 | 10.0% |
| 둘 다 초과 | 5.6% |
| **하나라도 초과 = 귀무가설** | **14.4%** |

14.4% 는 **무조건부** — 아무 날이나 골랐을 때의 값이다. 그런데 알림은 아무 날에나
나가지 않는다. 실제로 비교해야 할 값은 §7-7 이다.

### 7-7. ★ 조건부 귀무가설 — 알림이 나가는 날의 기저는 14.4% 가 아니다

`analysis/signals.py` 를 보면 신호마다 **시장 조건**이 걸려 있다.

| 신호 | 시장 조건 | 등급 |
|---|---|---|
| `signal_divergence` | `abs(reaction_ret) >= theta_m` = **0.80%** | 🔴 경고의 유일한 트리거 |
| `signal_tone_vs_vix` | `abs(vix_chg) >= theta_vix` = **1.00pt** | ⚠️ |
| `signal_tone_vs_rate` | `abs(ust2y_chg) >= theta_rate` = 0.05%p | ⚠️ |
| `signal_tone_shift` | **없음** (`abs(delta) >= theta` 뿐) | ⚠️ |

즉 🔴 알림은 **이미 시장이 크게 움직인 날에만** 나간다. 변동성은 군집하므로 그런 날의
다음 날은 원래 더 출렁인다. 14.4% 와 비교하면 그 군집 효과를 신호의 성능으로 오독한다.

**측정.** 고정 임계값(1.7771% / 2.401pt)은 그대로 두고 **비교 대상만** 바꿔,
2000-01-03~2026-08-25 · 6,698 거래일에서 t 일 조건별로 t→t+1 적중률을 셌다.
산출은 `analysis/conditional_null.py` — `outputs/hit_thresholds.json` 의 임계값과 표본
구간을 **읽기만** 하므로 재실행해도 값이 변하지 않는다. 무조건부를 재현하면 14.42% 로
등록값 14.43% 와 일치한다(경계 처리 차이로 마지막 자리만 다르다).

| 조건 (t일) | 걸리는 신호 | t→t+1 적중률 | n | 무조건부 대비 |
|---|---|---|---|---|
| 없음 | `tone_shift` | **14.4%** | 6,698 | 1.00배 |
| \|S&P\| ≥ 0.80% | `divergence` → 🔴 | **22.4%** | 2,384 | 1.55배 |
| \|ΔVIX\| ≥ 1.00pt | `tone_vs_vix` | **24.4%** | 2,367 | 1.69배 |
| 둘 중 하나라도 | ⚠️ 이상 대부분 | 21.9% | 3,092 | 1.52배 |
| **둘 다** | 7/29·8/20 형 🔴 | **26.0%** | 1,659 | 1.81배 |

**귀무가설은 하나가 아니라 신호별이다.**

- **기본 채널(🔴 = divergence) → 22.4%.** 기록상 🔴 두 건(7/29·8/20)은 둘 다
  `divergence`+`tone_vs_vix` 동시 발동이므로 그 형태의 기저는 **26.0%** 다
- **⚠️ 옵트다운 티어 → 14.4%.** 기록상 ⚠️ 는 전부 `tone_shift` 단독이고 이 신호에는
  시장 조건이 없다. 여기서는 무조건부가 그대로 맞다

**위기가 만든 값이 아니다.** 2008·2020 을 빼면 무조건부 12.8% · 조건부 19.5% 로 둘 다
내려가지만 비율은 1.52배로 사실상 같다. 조건부 프리미엄은 위기 몇 개가 아니라 변동성
군집 자체에서 나온다. 조교님 질문 4-4 에 대한 답이 여기서도 같은 형태로 준비된다.

**사전 등록을 훼손하지 않는다.** `outputs/hit_thresholds.json` 은 건드리지 않았고
적중 판정식도 그대로다. 바뀐 것은 **무엇과 비교하는가** 하나뿐이며, 알림을 한 건도
보내기 전에 고쳤다. 등록 내용을 무르는 게 아니라 더 엄밀하게 만드는 정정이다.

**§8-1 이 예시로 쓰던 "적중률 25%"는 이제 성과가 아니다.** 조건부로 보면 25% 는 기본
채널 기저(22.4%)와 거의 같다. 아무 정보 없는 신호도 25% 를 찍는다.

## 8. 한계

**8-1. 기본 채널의 적중률 유의성 판정은 프로젝트 수명 안에서 불가능하다.**
🔴이 월 1~2회면 1년에 12~24건이다. §7-7 로 기본 채널의 귀무가설이 **22.4%** 로
올라가면서 필요한 표본이 다시 크게 늘었다.

| 알림 수 | 25% 적중 시 p | 유의하려면 | (귀무 14.4% 였다면) |
|---|---|---|---|
| 20건 (약 1년) | 0.474 | 9건(45%) | p=0.153 |
| 40건 (약 2년) | 0.403 | 14건(35%) | p=0.054 |
| 60건 (약 2.5년) | 0.359 | 20건(33%) | p=0.021 |
| 200건 (약 8년) | 0.207 | 56건(28%) | p<0.001 |
| 800건 (약 30년) | 0.041 | 199건(25%) | p<0.001 |

**관측 25% 로는 어떤 현실적 기간에도 유의해지지 않는다.** "적중률로 성능을 입증한다"는
목표는 이 프로젝트에서 성립하지 않는다. 남는 주장은 둘뿐이다 — ① 기준을 사전 등록했다,
② 적중률을 **조건부 기저와 나란히** 보고한다. **유의성 주장은 하지 않는다.**

**막힌 것은 표본이 아니라 효과 크기다.** n 을 늘리는 길이 닫혔으므로, 유의해지려면
적중률 자체가 33%(n=60 기준) 이상이어야 한다. 그 정도가 아니면 "표본이 부족해서 못
밝혔다"가 아니라 **효과가 그만큼 없는 것**이다. 이 문장을 미리 적어두는 이유는, 나중에
낮은 적중률을 표본 탓으로 돌리고 싶어지기 때문이다.

**위 표는 관측이 독립이라는 낙관적 가정 위에 있다.** 이항검정은 알림 n 건이 서로
독립일 때의 값이다. 그런데 §7-7 이 보인 대로 알림은 변동성이 높은 국면에 몰리고,
몰린 알림들은 같은 국면을 중복해서 세는 셈이다. **실질 독립 관측 수는 n 보다 작으므로
실제로는 위 표보다 더 나쁘다.**

**올해 보고서에는 "적중률 X%"를 쓸 수 없고, "기준을 사전 등록했다"까지만 쓸 수 있다.**

**8-2. 발동 기준의 근거가 20일치다.** §2-1 의 빈도표는 2026-08-11~09-01 만으로
계산했다. 초판(15일)보다 5일 늘었을 뿐이고, 그 이전 `outputs/daily_signals.csv` 는
회의일 단위라 일별 빈도로 쓸 수 없다.

**8-2a. θ 가 아직 일별 척도로 재보정되지 않았다.** §2-1 표대로 `theta_shift` 는 월별
척도(0.95)를 일별 계열(p85=3.28)에 쓰고 있어 발동률이 설계값 15% 가 아니라 67% 다.
**이 상태로 알림을 켜면 ⚠️ 구독자에게 이틀에 한 번 메일이 간다.** θ 재보정은 구현
착수의 선행 조건이다(§10). 그리고 재보정은 뉴스 백필이 끝나야 의미가 있다 — 지금의
일별 분포 자체가 2026-07 이후 두 달치라 p85 가 아직 흔들린다.

**8-2b. 과거 신호 기록이 현재 지수로 재현되지 않는다.** `outputs/daily_signals.csv` 는
실행 시점에 누적되는 append-only 기록이고(질문 6 원칙), `outputs/daily_headline.csv` 는
뉴스 백필 이후 전 구간이 재계산됐다. 그래서 같은 날짜의 값이 두 파일에서 다르다 —
예를 들어 8/25 는 지수 +0.296 vs −0.935, 기사 30건 vs 14건이다. **과거 ⚠️ 행은 백필
이전 지수로 생긴 것이라 지금 다시 돌려도 같은 등급이 안 나온다.** §2-1 의 빈도는
"그때 실제로 나갔을 알림"의 빈도이지 현재 파이프라인의 빈도가 아니다.

**8-3. 표본 확대 우회로는 범위 밖이다.** 알림이 아니라 **등급 자체**를 과거로 소급
평가하면 표본이 커진다. 그러나 뉴스 축이 2026-07 부터만 존재해 Fed 축 단독 등급으로만
가능하고, 그러면 TA 질문 4(설명력 분석) 영역으로 넘어간다. 이 문서의 범위가 아니다.

**8-4. 도달 한계.** 자체 도메인 + SPF/DKIM 정렬로 스팸함 위험을 낮추지만(§6-2)
0 이 되지는 않는다. 새 도메인은 발신 이력이 없어 초기에 특히 그렇다.
**"보냈다"와 "읽혔다"는 다르다** — §7-1 의 `n_recipients` 는 **발송 시도 수**이지
도달 수가 아니다. 적중률을 해석할 때 이 구분을 흐리면 안 된다.

**8-5. 웹푸시를 구현하지 않는다.** §1 의 이유로 미뤘다. 보고서에 "다채널 알림"이라고
쓸 수 없고, 데스크톱 사용자가 사이트를 안 켜둔 시각에는 닿을 방법이 이메일뿐이다.
`channel` 필드를 남겨 확장 경로만 열어둔 상태다.

**8-6. 개인정보를 보관하게 됐다.** 웹푸시만 할 때는 없던 부담이다. §6-3 의 최소
수준으로 처리하되, **더블 옵트인을 생략했으므로 타인 주소 무단 등록 가능성이 남는다.**
수신거부를 한 번 클릭으로 만들어 피해를 줄이는 것이 유일한 완화책이다.

**8-7. 미결정 사항.** 도메인 이름과 구매 주체, Cloudflare 계정 주체, 구독 UI 위치.

### 범위 변경 기록 (2026-08-26, 같은 날 두 번)

**① 웹푸시만 → 웹푸시 + 이메일.**
초안은 이메일의 개인정보 부담과 인프라가 두 배라는 이유로 웹푸시만으로 좁혔다.
담당자 판단으로 뒤집었다 — **최종 웹사이트에 이메일 알림을 넣기로 이미 정해져
있었으므로**, 알림용 인프라를 따로 만드는 것보다 같이 쓰는 편이 낫다.

**② 웹푸시 + 이메일 → 이메일만 구현.**
웹푸시가 실제로 어떻게 도달하는지 확인한 뒤(§1 표) 좁혔다. 웹푸시는 인앱 배너도
앱 푸시도 아닌 **OS 알림**이고, 사이트를 안 켜두어도 오지만 조건이 붙는다 —
데스크톱은 브라우저가 켜져 있어야 하고 아이폰은 홈 화면 추가가 선행돼야 한다.
FOMC 발표 시각(KST 새벽 3~4시)에는 두 조건이 모두 어긋난다.

초안의 개인정보 우려 자체가 틀렸던 것은 아니므로, 그 대가를 §6-3(최소 수준 처리)과
§8-6(더블 옵트인 생략의 잔여 위험)에 남겨둔다.

### 변경 기록 (2026-08-27) — 주 기준 5거래일 → 1거래일

초판은 주 기준을 5거래일로 잡았는데 **근거가 없었다.** 팀 검토에서 "신호 직후의
변동이 더 의미 있는 것 아니냐"는 지적이 나와 재검토했고, 두 가지 이유로 1거래일로
바꿨다.

1. **기존 분석과 어긋나 있었다.** `analyze_alignment.REACTION_OFFSET = 1`,
   `backtest.N_DAYS = 2` 로 프로젝트 전체가 즉각 반응을 보는데 적중 기준만 5일이었다.
2. **1거래일이 더 강한 주장이다.** divergence 는 "어긋났으니 곧 정렬된다"는 신호이므로
   정렬이 빠를수록 신호가 정보를 가졌다는 증거가 강하다. 창이 길면 무관한 사건이
   끼어들 시간이 생긴다.

**임계값은 재계산하지 않았다.** 1·3·5·10거래일 네 개 모두 2026-08-26 에 이미
산출·고정돼 있었고, 그중 어느 것을 주 기준으로 선언하느냐만 바꿨다. 데이터를 보고
고른 것이 아니라 위 두 설계 원칙으로 고른 것이므로 사후 조정이 아니다.

귀무가설은 14.5%(5일) → **14.4%**(1일)로 사실상 동일하다. 분위수 기준이라 기간이
바뀌어도 난이도가 달라지지 않기 때문이다.

### 정정 기록 (2026-08-27) — 귀무가설 10% → 14.4%

이 문서의 초판은 §7-3 에서 "상위 10% 기준이면 무작위 적중률은 **정의상 10%**"라고
적었다. **틀렸다.** 주 기준이 "S&P **또는** VIX"인 합집합이라 두 축이 겹치는 만큼
발생률이 올라간다. §7-5 를 실제로 돌려보니 **14.4%** 였다.

같은 오류가 §8-1 의 검정력 계산에도 옮겨가 있었다. 10% 를 기준으로 잡으면 n=20 에서
p≈0.04 라 "1년이면 판정 가능"으로 보이지만, 14.4% 로 고치면 같은 조건이 p≈0.15 다.
**필요한 관측 기간이 1년에서 2.5년으로 늘었다.**

남겨두는 이유: 그대로 두었으면 보고서에서 적중률을 10% 와 비교해 성과를 1.45배
부풀렸을 것이다. §7-6 이 "계산해봐야 안다"고 미리 적어둔 덕에 잡혔다.

### 정정 기록 (2026-09-02) — 귀무가설을 무조건부 14.4% → 신호별 조건부로

팀 검토에서 "그 알림은 원래 시장이 흔들린 날에만 나가는 것 아니냐"는 지적이 나왔다.
**맞다.** `signal_divergence` 는 `abs(reaction_ret) >= 0.80%` 를 요구하므로 🔴 은
정의상 시장이 이미 움직인 날에만 나간다. 변동성 군집 때문에 그런 날의 다음 날은 원래
더 출렁이는데, 문서는 그 기저를 "아무 날"의 14.4% 로 잡고 있었다.

재측정 결과 **기본 채널의 귀무가설은 22.4%**(§7-7)다. 지적이 나온 시점의 추정은
"20% 대"였는데, 우리 판정식이 S&P **합집합** VIX 라서 실제로는 그보다 높았다.

두 가지가 따라 바뀌었다.

1. **§7-7 신설** — 귀무가설이 하나가 아니라 신호별이다. 🔴 22.4%(둘 다 터지면 26.0%),
   ⚠️(tone_shift 단독) 는 시장 조건이 없어 14.4% 그대로
2. **§8-1 전면 수정** — 관측 25% 는 조건부 기저와 거의 같아진다. 유의해지려면 n=800
   이 필요하다. **"적중률로 성능을 입증한다"는 목표를 접고** 사전 등록 + 조건부 기저
   병기까지만 주장하기로 했다

같은 검토에서 나온 세 가지도 함께 반영했다 — 네 기간 결과 병기 명문화(§7-2),
측정 창 시작점을 "발송일 종가"로 고정(§7-2), 이항검정의 독립 가정 한계(§8-1).

**임계값은 재계산하지 않았다.** `outputs/hit_thresholds.json` 은 그대로다. 바뀐 것은
비교 대상뿐이고, 알림을 한 건도 보내기 전이라 사후 조정이 아니다.

남겨두는 이유: 이 정정이 없었으면 보고서에서 "무작위의 1.7배"라고 썼을 텐데, 조건부로
보면 1.1배다. 앞선 10%→14.4% 정정과 **같은 종류의 오류가 한 겹 더 있었던** 셈이다.

### 재측정 기록 (2026-09-02) — 발동 기준: 원인 진단이 틀렸다

§2-1 의 빈도표를 20 거래일로 다시 셌다. 빈도 자체는 거의 그대로였지만(⚠️ 7→9건,
🔴 1→1건) **원인 진단이 틀렸다는 게 드러났다.**

초판은 ⚠️ 홍수를 "표본 적은 뉴스(하루 3~12건)가 흔들려서"로 설명했다. 실제 원인은
`theta_shift=0.95` 가 **월별** 결합 지수(std≈0.80)의 p85 인데 **일별** 계열(std 1.85)에
쓰이고 있다는 것이다. 발동률이 설계 의도 15% 대신 67% 다. 일별 p85(3.28)로 재보정하면
15% 로 돌아온다.

결론(🔴 기본값)은 유지하되 근거를 바꿨고, **θ 재보정을 구현 착수의 선행 조건으로
승격**했다(§8-2a, §10). 재보정 후에는 ⚠️ 를 기본값으로 낮출지 다시 판단한다.

부수적으로 `daily_signals.csv` 와 `daily_headline.csv` 가 같은 날짜에 서로 다른 값을
갖는다는 것도 확인해 §8-2b 에 남겼다.
